# Technical Interview Showcase: 아키텍처 리팩토링 설명 논리

이 문서는 크레버스 포트폴리오 프로젝트의 리팩토링 과정에서 도출된 소프트웨어 공학적 성과와 해결 논리를 정리하여, **기술 면접 및 포트폴리오 문서화(README/Wiki)** 시 직무 역량을 증명하기 위한 기술 리포트입니다.

---

## 1. UI 라이프사이클 & 메모리 누수 방지 (UIRootBase & UniRx)

### Q. UI 컴포넌트 설계 시 UniRx의 메모리 누수 문제를 어떻게 예방했나요?
*   **답변 핵심**: "최상위 UI 패널과 일반 UI 요소의 책임을 분리하고, 화면 활성/비활성 주기에 맞춘 구독 수명주기(Disposable Lifecycle)를 구축했습니다."
*   **설명 논리**:
    *   상용 프로젝트 포팅 과정에서 기존의 웹 플랫폼 결합 코드를 분리하는 과정에서 `UIRootBase` 클래스를 프레임워크 규격에 맞게 재설계했습니다.
    *   **최상위 UI 패널 (UIRootBase 상속)**: 켜지고 꺼지는(Show/Hide) 라이프사이클 및 화면 전환 애니메이션을 총괄하는 최상위 UI 컨트롤러는 `UIRootBase`를 상속합니다. 이들은 화면에서 일시적으로 숨겨질(Hide) 때 진행 중인 트윈 애니메이션을 즉시 중단(Kill)하고, `CompositeDisposable`을 통해 하위의 모든 이벤트 스트림을 명시적으로 해제(Clear)하여 메모리 누수를 원천 차단합니다. 그 후 다시 나타날 때(`Show`) 이벤트를 재구독(Resubscribe)합니다.
    *   **일반 UI 컴포넌트 (MonoBehaviour 상속 + Auto-Dispose)**: 개별 버튼, 토글, 컬러 칩 등의 단일 상호작용 컴포넌트들은 무거운 `UIRootBase` 상속을 피하고 `MonoBehaviour`를 유지합니다. 대신 UniRx 스트림 구독 시 **`.AddTo(this)`** 또는 **`.AddTo(gameObject)`** 패턴을 철저히 준수하여, 오브젝트가 파괴되거나 씬이 전환될 때 프레임워크가 가비지 컬렉터(GC)에 의존하지 않고 즉시 구독을 해제하도록 설계했습니다.

### 📐 UI 컴포넌트 상속 및 설계 표준 규칙

| 구분 | 상속 대상 | 주요 책임 | UniRx 구독 해제 방식 |
| :--- | :--- | :--- | :--- |
| **최상위 UI 패널** | `UIRootBase` | 화면 On/Off 수명주기 통제, 하위 컴포넌트 조율, 뷰 연출 | `ClearUIDisposable()` (Hide/Show 시점에 수동 트리거) |
| **일반 UI 컴포넌트** | `MonoBehaviour` | 단순 입력 감지, 개별 비주얼 상태(Color, Text) 렌더링 | `.AddTo(this)` (MonoBehaviour 파괴 시 자동 연동) |

## 2. 결합도 제거 및 Mock API 설계 (DIP)

### Q. 백엔드 통신이나 인프라 API가 불안정할 때 클라이언트 콘텐츠 개발을 어떻게 지속시켰나요?
*   **답변 핵심**: "의존 역전 원칙(DIP)을 활용해 REST API 및 웹 플랫폼 결합도를 격리하고, Zenject 컨테이너 기반의 Mocking 아키텍처를 도입했습니다."
*   **설명 논리**:
    *   기존 실서비스 코드는 플랫폼 백엔드(Azure Storage, REST API)와 게임 비즈니스 규칙이 강하게 결합되어 있어 백엔드 점검 시 콘텐츠 테스트가 불가능한 환경이었습니다.
    *   이를 해결하기 위해 통신 데이터 직렬화 및 데이터 저장을 추상화한 `IAPIService` 인터페이스를 정의하고, 실 배포용 `RealAPIService`와 로컬 RAM 상에서 에뮬레이션하는 `MockAPIService`로 구현을 분리했습니다.
    *   Zenject MonoInstaller를 통해 개발 및 에디터 테스팅 시에는 `MockAPIService`를, 배포 빌드 시에는 `RealAPIService`를 주입(Injection)하도록 설계하여, 백엔드 의존성 없이 클라이언트 콘텐츠 씬을 100% 독립 실행 및 QA 가능한 환경을 확보했습니다.

## 3. 데이터 기반 동적 스폰 및 레이아웃 타이밍 (Data-Driven & Async UI)

### Q. 수작업 씬 구성의 휴먼 에러를 방지하고 해상도 대응 버그를 어떻게 해결했나요?
*   **답변 핵심**: "ScriptableObject 기반의 데이터 중심 설계(Data-Driven)로 전환하고, UGUI 레이아웃 갱신 시차를 비동기 라이프사이클(UniTask)로 강제 동기화했습니다."
*   **설명 논리**:
    *   스테이지별 그리드 크기, 셀 프리팹, 사양 검증 로직 등의 정적 데이터를 C# 코드와 인스펙터 하드코딩에서 분리하여 `PlayableLevelData` ScriptableObject 에셋 자산으로 표준화했습니다.
    *   런타임 동적 스폰 시 UGUI의 `GridLayoutGroup` 정렬 연산이 한 프레임 지연되면서 셀 크기가 찌그러지거나 좌표를 잘못 읽는 타이밍 버그가 발생했습니다.
    *   단순 시간 지연(Delay) 방식 대신, 스폰 직후 `ForceRebuildLayoutImmediate`를 가동해 UGUI 정렬을 즉시 동기화 강제하고, 렌더링 확정 시점(`LastPostLateUpdate`)까지 UniTask 비동기 Yield를 주입함으로써 창 해상도 리사이징 시에도 다이내믹하게 그리드 프레임이 셀 정위치를 추적하도록 가변 트래킹 연산을 고도화했습니다.

## 4. 에디터 툴체인을 활용한 포팅 공정 자동화 (Scene-to-Prefab Pipeline)

### Q. 씬 기반 개발과 프리팹 기반 런타임의 충돌을 어떻게 해결했나요?
*   **답변 핵심**: "개발용 단독 씬에서 비주얼을 수정하고 저장하면, 에디터 스크립트가 이를 감지해 자동으로 최적화된 런타임 프리팹으로 구워내고 데이터 Outline에 매핑해주는 자동화 툴체인을 구축했습니다."
*   **설명 논리**:
    *   개별 게임 씬(`.unity`)을 매번 씬 빌드 리스트에 등록하고 LoadScene하는 방식은 씬 간의 컴포넌트 유실, EventSystem 중복, 라이팅 세팅 불일치 등의 런타임 크래시를 유발하고 메모리를 크게 낭비합니다.
    *   이를 해결하기 위해 실제 런타임 구동은 **프리팹 동적 스폰(Instantiate) 방식**으로 전환하여 씬 충돌을 원천 차단하고 로딩 시간 및 GC Alloc 성능을 극대화했습니다.
    *   하지만 프리팹을 수동으로 빌드/갱신하는 것은 개발자의 번거로움과 업데이트 누락(휴먼 에러)을 유발하므로, 유니티 에디터 스크립트를 확장해 **개발용 씬의 콘텐츠를 단 한 번의 클릭으로 런타임용 프리팹으로 자동 빌드(PrefabUtility.SaveAsPrefabAsset)하고 LessonOutline 데이터 자산에 주입**해 주는 `Scene-to-Prefab` 자동화 시스템을 완성했습니다.
    *   이로 인해 개발 생산성은 유지하면서도 최종 빌드의 성능과 무결성을 동시에 확보했습니다.
